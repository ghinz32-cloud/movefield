# Security, privacy and data-integrity audit — 16 October 2026

The initial read-only audit found five reproducible defects: retained old-key history after a web passphrase change, a large recovery-bundle import limit mismatch, silent setup-draft overwrites between web tabs, a false corruption error during a concurrent record read, and a stale cloud-queue discard. Current records were preserved in the recovery/read tests; the draft and queue tests demonstrated loss of the newer draft/queued operation. A subsequent authorized repair phase corrected these paths and added targeted preservation regressions. Original failure evidence is retained below; it must not be mistaken for the status of the repaired candidate.

The original source checkpoint is `f0130487760aa03d64b22f23002da5423da7ff4e`; the repair phase began after delivery source `920a73621d9f2ab15bbddcd00139c9cebd155238`. Movefield and Grizzly share the affected record modules. The native snapshot matched the canonical record/vault/schema/preservation/cloud-sync/selection files checked in the baseline audit. The audit captured SHA-256 hashes for 30 source/lock files in `.sites-runtime/comprehensive-security/source-hashes.json`. New repair receipts capture their actual source or served asset hashes separately. Concurrent release documentation/download packaging is outside the original source hashes.

The actual-browser cases used disposable synthetic profiles at the local copies of `/movefield/review/` and `/movefield/grizzly/`, with Chromium's sandbox enabled. The two-tab receipt records the served JS/CSS hashes. These are current shared websites, not the older preserved original Pages root. No live Cloudflare/Google/AI account, secret, real user record, third-party penetration probe, or physical phone was used. The owner `.openai/` directory was excluded.

### SEC-01 — Passphrase rotation retains history encrypted with the old passphrase

**Evidence:** `app/page.tsx:207–216` installs a fresh vault and record writer. `lib/record-state.ts:79–82` prunes only the new vault ID; `lib/browser-records.ts:19` scopes the deletion cursor to that ID. No successful-rotation cleanup removes the superseded vault's rows. `components/vault-controls.tsx:8` reports success and warns about older *downloaded* backups, but these retained rows are still in the app's normal IndexedDB database.

**Reproduction, both brands:** create a private profile with one saved workout and a note; use the real **Change vault passphrase** control; wait for success; inspect the database's `rows` store. The current root correctly rejects the old passphrase and accepts the new one. There are nevertheless two history rows: one for the new vault and one for the previous vault. Deriving a key from the old passphrase and the retained old envelope still decrypts the old note and load. This requires access to the local database and the old passphrase; it does not unlock the new root or provide a remote attack by itself.

**Impact:** changing a compromised passphrase does not retire access to historical records still held by the app. Repeated rotations/restores can also accumulate abandoned ciphertext. This is observable retention through normal IndexedDB APIs, not speculative disk remanence. Native's separately documented recovery-key ring is an intentional interruption-recovery mechanism and was not treated as the same finding.

**Proposed repair:** after the new root, all replacement history and the legacy projection have been durably verified, remove superseded-vault rows in a guarded database transaction that checks the expected current root. Preserve the original data on encryption, commit or projection failure. Test populated history, repeated rotation, concurrent writers, interrupted cleanup, wrong/new passphrases, rollback and independent brand storage. Do not delete old data before the replacement is verified. Downloaded backups remain separate copies.

**Fresh evidence:** `.sites-runtime/comprehensive-security/rotation-retention-result.json`, checked `2026-10-16T19:02:38.219Z`; reproducer `reproduce-rotation-retention.mjs` in the same directory. Both actual UI journeys reproduced the defect with no browser errors.

### SEC-02 — Valid large record-recovery bundles cannot be opened

**Evidence:** `lib/record-state.ts:94` and `:100` call `isVault(raw)` before parsing a bundle. `lib/vault-format.ts:16` rejects any input longer than 10,002,000 characters. The subsequent bundle parser explicitly permits 32 MiB (`lib/record-state.ts:95`, `:101`). `encryptedRecordBundle` at `:87–91` can produce a valid bundle above the envelope limit. Web restore reaches this path through `components/vault-backup.tsx:15`; native `previewLocalBackup` reaches `decodeRecordBundle` through `mobile/src/storage.ts:104–105`.

**Reproduction:** create a schema-valid state with 5,000 historical workouts and bounded notes. State size was **3,634,711 bytes**, below the 5 MB state cap. The actual shared record writer and AES-GCM implementation saved and reopened it without a change. Export produced **12,275,544 bytes**, below the advertised **33,554,432-byte** bundle limit. Both `recordBundleRoot(bundle)` and `decodeRecordBundle(bundle, crypto)` failed with `Encrypted file exceeds the supported size.` A fresh read of the existing saved records still succeeded exactly.

**Impact and limits:** this breaks the complete original-record recovery path for sufficiently populated archives, including a file exported for recovery. It does not prove that every 5,000-record archive fails: size depends on recorded content. The normal unlocked **Download/Export encrypted backup** writes a whole-state envelope (`app/page.tsx:245`, `mobile/App-runtime.js:1709–1712`) and is not this multi-record bundle path. Do not describe all normal backups as broken. Recovery is particularly important when only the original bundle remains available.

**Proposed repair:** separate bounded format detection from single-envelope size enforcement, or parse the bounded outer bundle before applying the tighter limit to its individual envelopes. Keep the 32 MiB outer limit, 5 MB reconstructed-state limit, record-count bounds, exact digest/identity checks and authenticated metadata. Add a real >10 MB/<32 MiB archive round trip plus above-limit/malformed/tampered/missing-row failures, using the shared implementation and copied native snapshot.

**Fresh evidence:** `large-bundle-result.json`, checked `2026-10-16T18:55:28.134Z`, and `reproduce-large-bundle.cjs` under `.sites-runtime/comprehensive-security/`. The backend in this reproduction is synthetic memory; the schema, encryption, record writer and decoders are real. It is not a phone-performance or native-bridge test.

### SEC-03 — Setup drafts lack cross-tab compare-and-swap

**Evidence:** `app/page.tsx:260` serializes draft writes under Web Locks but compares only the accepted profile ciphertext. It does not compare the previous setup ciphertext or revision. The storage listener at `app/page.tsx:154` observes the main personal-state key, not the setup key. `components/training-onboarding.tsx:41–44` keeps each tab's separate in-memory draft and saves the whole object on input changes. Draft clearing also lacks an expected-draft comparison.

**Reproduction, both brands:** open an encrypted profile's builder in tab A and enter a name. Open the same builder in tab B; B restores that draft. B changes and saves the name. A still has the older name, then changes only age. A writes its entire stale draft and silently removes B's newer name. Reloading B restores the old name and A's age. Neither tab showed a conflict warning. The accepted profile ciphertext remained unchanged.

**Impact:** unfinished answers can disappear even though each write reports normal saving. Serialization prevents simultaneous writes from overlapping but does not prevent a stale full-object write. This is draft loss, not demonstrated workout-history loss.

**Proposed repair:** maintain an expected encrypted draft/revision after reading and each acknowledged write; compare it under the existing lock before writing or clearing. On mismatch, preserve the tab's entered values and the latest stored draft and offer an explicit review/reload choice. Do not silently merge conflicting profile/equipment/calendar choices. Test separate edits, conflicting edits, explicit close, accepted-plan changes, stale clear, reload, quota failure and both brands.

**Fresh evidence:** `draft-tabs-result.json`, checked `2026-10-16T18:58:31.603Z`, and `reproduce-draft-tabs.mjs` under `.sites-runtime/comprehensive-security/`. Two real tabs used actual WebCrypto, IndexedDB, localStorage, Web Locks and rendered controls. Both brands reproduced the defect; there were zero browser errors. The receipt contains exact JS/CSS identities and screenshots accompany it.

### SEC-04 — Record reads are not an atomic root-and-row snapshot

**Evidence:** `lib/record-state.ts:45–46` reads the root, then asynchronously decrypts it and separately obtains its rows (`:25–34`). `lib/browser-records.ts:10–11` and `lib/sql-records.ts:6–7` implement those calls separately. A writer can commit an edited row and prune the old ciphertext (`lib/record-state.ts:73–82`) between them. The existing atomic `snapshot()` implementations are used for export, not this normal read.

**Reproduction:** delay a reader after it captures an old root. A second writer commits a changed historical set and prunes its previous row. Resume the first reader. It raises `A saved workout is missing or changed. Preserve the original archive and restore a verified backup.` A new reader immediately recovers the exact committed state. No record was deleted from the current root's archive.

**Impact and limits:** a valid concurrent save can appear to be archive corruption and send a user toward recovery. The controlled reproduction exercises the real shared crypto/reader/writer against a synthetic backend interleaving. It demonstrates the shared protocol issue, not a physical-phone race frequency. Native's common single writer reduces ordinary opportunities; web tabs provide multiple readers/writers. Existing true-corruption checks should continue to fail closed.

**Proposed repair:** decode a consistent backend snapshot, or detect root change and perform a bounded retry from a fresh root before reporting corruption. Bind the writer's expected version/cache to the successful snapshot. Add both a concurrent-edit/prune case and a genuinely missing/tampered-row case so a retry cannot mask corruption.

**Fresh evidence:** `record-read-race-result.json`, checked `2026-10-16T18:58:51.820Z`, and `reproduce-record-read-race.cjs` under `.sites-runtime/comprehensive-security/`.

### SEC-05 — Signed-in queue discard omits its supported expected-operation guard

**Evidence:** the web outbox's `clear(expected)` already checks the exact encrypted operation under a Web Lock (`components/cloud-account.tsx:19`). The signed-in **Discard queued upload** callback reads the queue, awaits account verification, then calls `outbox.clear()` without that captured value (`:34`). The native equivalent calls `nativeOutbox.clear()` without its read value (`mobile/src/cloud-account.tsx:35`); native storage already supports the expected-operation check (`mobile/src/storage.ts:148`). Retry acknowledgements and signed-out discard correctly pass the expected operation.

**Reproduction:** render the actual web `CloudAccount` with real BrowserVault/localStorage/Web Locks and synthetic capabilities/session responses. Begin discarding operation A; pause the session check; replace the queue with valid operation B as a second writer could after finishing A; release the session check. The UI says the upload was discarded, and B is gone. The private profile ciphertext is unchanged. No live service is contacted.

**Impact and limits:** a newer requested upload loses its retry record. This does not expose ciphertext plaintext or change the cloud copy by itself. The current GitHub Pages installation and native qualification flags keep these services disabled, so this is a required repair before enabling configured accounts rather than a currently active Pages upload failure. The native callsite has the same omission, but a native multi-writer UI reproduction was not performed.

**Proposed repair:** clear only the non-null captured raw operation, pass it to the already available comparison guard, and preserve/report a changed queue. Add the same owner-change, missing-queue and newer-operation cases to both UI adapters. Do not weaken the existing idempotent retry acknowledgement checks.

**Fresh evidence:** `outbox-discard-result.json`, checked `2026-10-16T19:00:05.305Z`, and `reproduce-outbox-discard.mjs` under `.sites-runtime/comprehensive-security/`.

## Current controls and remaining trust boundaries

- **At-rest encryption:** `lib/browser-vault.ts:6–28` uses nonextractable WebCrypto AES-256-GCM keys, 96-bit random nonces, 128-bit tags, a random 128-bit salt and fixed PBKDF2-SHA256 600,000 iterations. Authenticated metadata binds vault identity, type/purpose/schema/KDF. Native `mobile/src/storage.ts:18–55` uses Expo Crypto AES-GCM and SecureStore `WHEN_UNLOCKED_THIS_DEVICE_ONLY`, refuses silently minting a replacement key over encrypted data, and keeps recovery metadata bounded. These observations are not an independent cryptographic certification.
- **Record integrity:** authenticated root/history IDs plus ciphertext digests, backend CAS transactions, failed projection rollback, bounded plaintext/schema inputs, unknown-load preservation and immutable completed-record identities provide meaningful protection. SEC-01, SEC-02 and SEC-04 identify gaps beyond the existing successful regression cases.
- **Imports and exports:** current and legacy encrypted backups are validated before replacement; legacy transfer import additionally uses `readPreservedState` to reject silently discarded old fields. Plan import supplies new IDs and tracking authority. React text rendering is used for imported text; web/native form-reference URLs require HTTPS without embedded credentials (`components/exercise-guide.tsx:8`, `mobile/src/content.ts:7–8`). Explicit plaintext plan/profile exports remain user-controlled data disclosure and cannot be recalled after sharing. Native export cache files expire through app-owned cleanup; that is not a forensic-wipe guarantee.
- **Cloud identity/authorization:** server identity comes from the verified SDK session, never the expected-owner header alone. Google ID-token verification uses fixed JWKS/issuer/audience/algorithm/lifetime/authorized-party checks, PKCE/state and disabled implicit linking. Provider access/refresh/ID tokens are not retained in account rows; public session DTOs omit opaque tokens. Sessions expire, can be revoked, and sensitive revocation requires fresh authentication. Anonymous/foreign-owner/method/origin tests passed locally.
- **Offline and disabled services:** static `lib/cloud-client.ts:6` returns false capabilities and refuses other account actions; native `mobile/src/cloud-client.ts:8–14` requires an exact HTTPS origin plus qualification flag. `lib/server/auth.ts:14–18` requires explicit enablement, allowance verification, bindings and credentials. No new cloud/provider activation occurred. `public/movefield-sw.js:26–33` caches only approved same-origin GET shell/static paths, excludes query/API/business responses, and waits for old windows to close before updating. Private training remains in client memory/storage rather than private SSR.
- **AI boundary:** current offline coaching is deterministic. The future `lib/coaching-selection.ts` adapter is unconnected and selects only verified local message IDs with exact policy/context/digest, preserving required messages. Existing cloud highlights remain the separate three-fact protocol. `lib/server/coaching.ts:6–22` bounds input/output, reserves budgets before dispatch and rechecks consent/revision before publishing; arbitrary provider prose cannot become a prescription. No records were sent to a live AI service by this audit.
- **Secrets and privacy:** a scoped search of application/client sources found server credential symbol references only in server modules and environment type declarations; no client secret value was retrieved or printed. This is not a complete historical secret scan. No analytics/telemetry integration was found in the reviewed application paths. Unlocked memory, keyboard/app-switcher exposure, operating-system backups, exported copies, hosting logs and provider/operator retention remain separate boundaries. Encryption does not protect an already compromised unlocked origin or device.
