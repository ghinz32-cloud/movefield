### N-01 — Reminder opt-out in sample mode does not cancel personal alerts

**Evidence:** `mobile/App-runtime.js:588` calls `useNativeWorkoutReminders(sampleMode ? null : state, ...)`. `mobile/src/workout-notifications.ts:24` returns before reconciliation when `state` is null. The cancellation loop starts at line 28, and the disabled-preference branch is at line 32. `mobile/src/settings.tsx:39` updates the shared reminder preference to false and immediately reports “Workout reminders are off.” Settings remain available in sample mode.

**Reproduction:** Create one future scheduled personal workout and enable reminders. Switch to the sample profile, open Settings → Workout reminders, and turn reminders off. The real hook was executed with an in-memory notification adapter: one notification was scheduled before the switch; passing `state=null` and `reminders=false` left one scheduled notification and made zero cancellation calls. Returning to personal mode with the same false preference canceled it. Pending scheduling work also retains the old generation because the null-state branch returns before incrementing it.

**User impact:** A user explicitly turns alerts off, receives confirmation, and may still receive a personal workout reminder while remaining in the sample. This does not mutate workouts or history. It is an opt-out correctness issue affecting the shared implementation for both brands.

**Recommended correction:** Reconcile an explicit disabled preference even without an active personal `State`, once preferences are loaded. Invalidate pending schedules and cancel only this brand's owned reminder identifiers. Decide explicitly whether merely entering sample mode retains personal reminders; disabling them must work in either mode. Do not cancel another app's notifications or silently re-enable the preference on return.

**Required regression:** Both brands; personal scheduled reminders → sample → off; off while an OS schedule call is delayed; return to personal; permission denial/revocation; cancellation failure. Assert no newly scheduled/remaining owned alerts after successful opt-out and accurate error status if cancellation fails. Then verify delivery/cancellation on real Android and iOS.

### N-02 — Decimal-comma setup input is converted into `NaN`

**Evidence:** `mobile/src/plan-setup-runtime.js:37` requests `decimal-pad`. The optional “Heaviest ONE dumbbell” callback at line 124 calls `toKg(Number(v), p.units)` without comma normalization. Generic numeric setup fields at line 109 also use `Number(v)`. In contrast, `mobile/src/numeric-input.tsx` accepts comma and dot drafts and only publishes finite values; existing equipment settings at `mobile/App-runtime.js:271` normalize commas.

**Reproduction:** In the actual PlanSetup callback harness, reach Your dumbbells and enter `12,5` in “Heaviest ONE dumbbell (lb) · optional”. Observed output was `displayed: "NaN"`, a nonfinite `profile.dumbbellMaxKg`, and the real `readSetupDraft` validator rejecting the next save. The UI then reports “Setup could not be saved.” Accepted training was not changed.

**User impact:** A locale-appropriate decimal separator can break an otherwise valid setup. The entered text is replaced by a technical value; finishing or closing the draft is blocked until corrected. This is especially confusing on a phone keyboard that naturally presents a comma.

**Recommended correction:** Reuse the native numeric-input behavior, with blank/unknown distinct from zero/unavailable, finite-value publication, appropriate bounds, and conversion of one dumbbell to kilograms only after parsing. Integer-only fields should retain understandable validation without saving nonfinite values. Preserve the draft string while the user is still typing a separator.

**Required regression:** `12.5` and `12,5` in both lb/kg, blank, zero, partial decimal drafts, invalid signs/text, upper bounds, close/reopen, and failed-write retry. Assert identical finite conversions for comma/dot; no `NaN` rendered or serialized; accepted state remains unchanged until acceptance. Check actual iOS and Android decimal keyboards in a comma locale.

### N-03 — Larger exported backups cannot be recovered through the native importer

This finding is owned by the security/data audit, not independently reimplemented here. Its reproduction used 5,000 valid history records: the state saved and reopened, and its exported encrypted bundle was 12,275,544 bytes. Import then failed because `recordBundleRoot` / `decodeRecordBundle` first call `isVault(raw)`, applying the smaller envelope cap before the record-bundle parser's 32 MiB limit.

**Native integration:** `mobile/src/storage.ts:105` routes `previewLocalBackup` through `decodeRecordBundle`; the shared checks are at `mobile/src/shared/record-state.ts:94` and `:100`. The security reproduction receipt is `.sites-runtime/comprehensive-security/large-bundle-result.json`. Current records are retained on failure, but successful export cannot currently be treated as proof that a large backup will restore.

**Required outcome:** Align envelope/bundle detection and bounds without weakening size or schema validation; test real production-shape encrypted bundles below/at/above each limit, including export → fresh-device preview → verified restore. Retain the original local state on rejection. Keep this issue visible in native backup qualification and follow the security report's authoritative fix plan.

### N-04 — Rotation, multitasking and lateral insets need an explicit platform policy

**Evidence:** `mobile/app.json:6` requests portrait orientation and line 10 enables tablet support. The installed Expo orientation transforms produce portrait/upside-down for iPhone, all four orientations for iPad, and `UIRequiresFullScreen=false`. Thus the source does not actually limit every Apple window to a narrow portrait phone. The main shell at `mobile/App-runtime.js:1579` applies only top/bottom safe-area edges; ModalFrame at line 164 uses the default complete safe-area view. No `WindowInfoTracker`/`FoldingFeature` integration was found in the native application files.

An older, separately qualified Movefield 0.1.6 manifest at `.sites-runtime/coaching-2026-10-16/native-installers/movefield/local-evidence/manifest.xml` records portrait orientation, `configChanges=0x80000fb0`, and `windowSoftInputMode=0x10` (adjustResize). This supports understanding the previous template behavior; the current release manifest still requires its own inspection.

**Impact and limits:** A phone mounted horizontally cannot rely on app rotation. iPad multitasking and large Android/foldable windows can still expose wide/short layouts. Main-shell controls do not explicitly consume left/right cutout insets, while modal screens do. A missing hinge-aware layout is not proof of a failure on every foldable: many devices expose one uninterrupted usable display. Physical occlusion, posture transitions, activity recreation and OEM letterboxing remain unqualified.

**Recommended correction:** Adopt and test an explicit responsive orientation policy, consume lateral insets at the main-shell boundary without double-padding modals, and define behavior for a separating hinge or occluded display area. Preserve active workout, draft, focused exercise/set and pending save status across window changes. The foldable/responsive audit owns geometry results and layout recommendations; do not duplicate its browser-resize evidence as a hardware result.

**Required regression/device gate:** Phone portrait/landscape, iPad split view and window resizing, foldable cover → inner display → cover with keyboard open, tabletop posture, side-by-side app mode, screen-reader focus continuity, and activity recreation during input/save. Assert that no primary action or input sits under a cutout/hinge and no staged record is silently replaced.

### N-05 — Notification-denial recovery stops at instructional text

`mobile/src/workout-notifications.ts:14` and `mobile/src/rest-alerts.ts:19` request permission only on explicit user actions and correctly explain that notifications can be off. No `Linking.openSettings` or equivalent action is present in the native UI. A user whose OS refuses another permission prompt is told to check phone settings without an app-provided route there.

Add a small “Open phone settings” action when permission cannot be requested again, retain the timer when alerts are denied, and refresh permission status after returning. Verify system-level notification permission and per-channel/sound settings separately; granted permission does not guarantee audible delivery. This is a usability gap, not evidence that the OS permission request itself fails.

### N-06 — Unexpected render failure has no app-level recovery boundary

The root tree in `mobile/App-runtime.js:2309` supplies safe-area/appearance providers and the training UI. No application `componentDidCatch` or `getDerivedStateFromError` boundary was found in App or adjacent native components. Known saved-data failures correctly use a dedicated recovery screen, but a later rendering exception has no equivalent app-owned fallback.

For a later resilience pass, add a small boundary that preserves storage and offers a safe reopen/retry path, with a non-secret diagnostic code. It must not erase or replace records, and it must not imply that re-rendering recovers an uncommitted write. Test an injected child render failure with an existing synthetic history and active workout. No current production render crash was reproduced here; this is a hardening gap.

## Novice-facing improvements supported by this audit

1. Make the distinction between “saved on this device” and “a recoverable off-device backup” discoverable after a first real saved workout. Keep it a dismissible action rather than permanently expanding the workout screen. A phone replacement, uninstall or lost device key is not handled by ordinary Android backup because that is intentionally disabled.
2. Provide a guided backup verification flow after fixing N-03: select/export encrypted file, store the separate recovery material, verify a fresh preview, then show the last verification date. Do not state that a completed share sheet proves the file reached a chosen destination.
3. Use the same locale-aware number entry in setup, logging, limits and measurements. Keep unknown loads distinct from zero and explain one-dumbbell versus total load at the relevant input.
4. Give notification denial a direct settings route, and show whether alerts are enabled, denied, quiet/provisional, or failed to schedule. Preserve ordinary logging and the visible timer in every permission state.
5. Keep a concise offline explanation on external references and a recoverable error when they fail. The current written guide remains usable offline; an external browser reference is a different capability.
