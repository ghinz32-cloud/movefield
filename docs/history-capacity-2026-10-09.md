# Bounded history capacity

Stored profiles and plain backups accept at most 24,000,000 UTF-16 characters and 24,000,000 UTF-8 bytes, with the existing strict 5,000-workout schema limit. The general JSON/profile reader retains its 5,000,000-character default. `readStoredSavedState` opts into the larger bounded profile contract explicitly. Protected transfer files have a 96,000,000-byte/file-character envelope bound; decoded ciphertext is separately bounded before password derivation or decoding.

Native history remains individually encrypted in existing SQLite entity slots. The native adapter validates the full profile before splitting, bounds cumulative reconstructed plaintext before assembling it, and no longer applies the old whole-record envelope ceiling to a profile that is written as bounded entities. Original ciphertext identities, transactions, key transitions, rollback/readback and restore recovery remain unchanged.

`node scripts/check-history-capacity.cjs` passes 30 checks with 5,000 strict-schema workouts: 8,664,825 JSON characters, 8,665,143 UTF-8 bytes and a 17,330,671-character protected transfer. It exercises actual validation, cryptography, native splitting and a real SQLite host harness, including a fresh module/connection reopen, profile-only edits that leave all history ciphertext unchanged, and oversized input that cannot advance the saved revision. The fixture and receipts are reproducible; these are not phone/OS restart, memory, latency or physical-device capacity measurements.

Additional checks passed: web/native TypeScript, scoped ESLint, 62 transfer checks, three export-cancellation scenarios, and all 27 native-history scenarios/192 assertions. Schema compatibility changes are a required adjacent integration: the schema agent adds the explicit bounded-reader argument, strict field validation and record metadata. The historical backup test that expects unknown fields to be stripped must follow that schema contract.

Browser history now uses authenticated encrypted heads and individually encrypted workout rows in the existing IndexedDB version-2 stores. A warm profile-only edit neither reads nor rewrites history rows; a newly completed workout seals one new entity. Changed entities, retired entries, the new head and optional encrypted account outbox commit in one transaction. Existing plaintext/whole ciphertext migrates through the verified legacy import; the old whole ciphertext remains authoritative if the entity transaction aborts. Unknown/orphan ciphertext prevents silent first-key creation. Explicit approved restore/reset retires all owned history rows and preserves unrelated records.

History containers have a separate 26,000,000-character/UTF-8-byte bound for up to 5,000 hashed IDs/digests. Their inner state and reconstructed full profile remain limited to 24 MB. This prevents wrapper overhead from making an otherwise valid profile unreadable. Native hexadecimal record envelopes permit 52,002,048 bytes including fixed metadata. Transfers still contain the compatible full profile, within the original 24 MB profile contract and 96 MB protected-file bound.

`node scripts/check-browser-history.cjs` passes seven scenarios/53 assertions using actual source, fake IndexedDB transactions and real AES-GCM. It covers 5,000 records above the former ceiling, fresh-vault reopen, unchanged ciphertext, one completion, migration/queue rollback, stale saves, missing/corrupt/digest-mismatched entities, missing/same-shaped replaced keys, orphan cleanup and atomic reviewed-outbox reconciliation. Existing record-store 76, transactional vault 163, legacy vault 133 and outbox 67 checks remain green, along with web/native types and scoped lint. The updated backup suite refuses unknown future fields without modifying its input and passes seven checks.

The typed vault exposes `write(slot,text,expected,sync?)`, queue claim/receipt/failure/revision methods, and `reconcileSync({accountId,revision,expected})`. Reconciliation compares the exact validated full outbox inside the transaction, clears only the reviewed account pending work, sets its revision and preserves other accounts. A late receipt or another tab's queue change causes a conflict instead of silently discarding it.

`recoveryCopy(): Promise<string>` returns `{format:'movefield-browser-recovery-v1',revision,keyRevision,records}` with all owned fixed slots and nonempty history ciphertext, including orphans. It exports no key bytes and performs no decryption, so key-loss recovery retains all source ciphertext. This forensic recovery format is separate from a compatible protected transfer. Root must use it instead of exporting a lone head.

Root owns final UI integration, shared snapshot regeneration, reconciliation and publication. This document describes a local tested source checkpoint, not a deployed build.

Independent local-sync peer review found no material defect in dynamic CAS, key/orphan retirement, atomic queue writes or reviewed account reconciliation. Warm cached history assumes supported writers advance the stored revision. A fresh vault verifies all entity authentication/digests; unsupported out-of-band entity modification with unchanged head/revision may remain cached until reopening.
