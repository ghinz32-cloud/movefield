# Personalized workout coaching backend

This milestone adds an explicit, consented coaching contract for a saved completed workout or a fully logged lift in an active workout. The existing metrics-only `/api/daily-feedback` contract and its saved receipts remain compatible. Coaching uses a separate `workout_ai_coaching` table and the shared policy `workout-coaching-v1`; it does not change training automatically or expose provider-generated prose.

## Integration and migration

Apply the additive `drizzle/0001_workout_coaching.sql` migration, including the generated Drizzle journal and snapshot, to the existing D1 `DB` before activating this server version. It creates only `workout_ai_coaching` and its owner/creation index; it does not modify or delete existing sync or daily-feedback rows. Both AI routes now atomically share the same quota, so this version's v1 quota queries also require the new table. Deploy the migration and application together through the existing hosting process; do not enable the application first against an unmigrated database.

The deployment requires the existing dispatch-owned Sites ingress and server setting `MOVEFIELD_TRUST_SITES_AUTH=1`. All coaching GET/POST requests require `X-Movefield-Client: web`, same-origin authentication, and `X-Movefield-Expected-Account` matching the trusted ingress owner. POST additionally requires a matching Origin. The expected-account value can reject a changed account but cannot select a tenant; SQL uses only the trusted owner. The guard runs before a D1 session is opened. Native bearer authentication remains unsupported, and static Pages cannot serve this backend.

`GET /api/account` adds `coachingAvailable:boolean`. The existing settings `MOVEFIELD_AI_BASE_URL`, `MOVEFIELD_AI_API_KEY`, and `MOVEFIELD_AI_MODEL` are server-only. The compatible HTTPS provider must use the existing reviewed host allowlist; redirects, custom ports, URL credentials, query strings and fragments are refused. No credential, provider account or model-quality result is supplied by this milestone. Missing configuration reports `coachingAvailable:false` and HTTP 503 without creating a new job.

## Request and result contract

The canonical shared context is defined and validated by `lib/workout-coaching.ts`. Its application builder excludes names, free-text notes and full plans/history. It includes bounded logged performance, up to three comparable prior records per selected exercise, a 28-day attendance summary, minimal adult profile categories, current binding information, and application-authored observations and review choices. A completed workout has a real completion timestamp. A lift keeps `completedAt:null` and names the fully logged target exercise without inventing workout completion. Eligibility, symptom unknowns, attendance uncertainty and comparison limits remain explicit in the shared contract. These are consented client-derived facts, not independently verified clinical facts or server-decrypted account records.

`workoutCoachingDigest(context)` hashes the exact UTF-8 canonical serialization. `workoutCoachingRequestId(accountId,digest)` creates a domain-separated UUIDv8 binding policy, authenticated owner and context. Reopening or retrying unchanged context produces the same receipt, while a changed owner or context produces a different identity. The helpers use portable Noble hashes and no browser/Node global.

`POST /api/workout-coaching` accepts only `{requestId,contextDigest,context,consent:true}`. The strict context has a 12,000-byte canonical ceiling; the complete request is limited to 16,384 UTF-8 bytes. Unknown fields, malformed context, changed digest, non-deterministic new request IDs and future completion timestamps are refused. There is no arbitrary prompt, model or endpoint override.

Every status response includes `{policy,requestId,workoutId,contextDigest,status}`. Pending/processing responses include only a bounded `retryAfterMs` of 1,000–15,000 milliseconds, with no result. `GET /api/workout-coaching?id=<UUID>&context=<SHA256>` checks both owner and context before returning or scheduling a job. An exact duplicate POST returns the same saved job. Reusing the receipt with changed context conflicts.

A successful result is `{policy,workoutId,contextDigest,observationIds,reviewIds,priority}`. Only unique IDs already supplied by the application are accepted, with one to six observations, zero to three review choices and one fixed priority enum. Additional prose, fields, targets, patches, invented IDs, wrong context, truncated generation, tool calls and refusal output are rejected. The client validates the result again against its current context. Application-authored text renders those selections; required uncertainty/limit observations remain visible. Review choices require the existing separate preview and user approval. This is a constrained model-selected focus over grounded facts, not model authority to calculate or apply a training program.

## Durable processing, cancellation and retry

New jobs are saved before processing is scheduled through the Worker lifetime extension. A conditional SQL lease permits one processor, including after an interrupted Worker. Each operation has an eight-second provider timeout, a 16,384-byte streamed provider-response ceiling and no redirects. At most three attempts are persisted, with five seconds per failed attempt of persisted backoff. Polling may resume eligible pending or expired processing jobs; the final expired lease becomes terminal. A changed configured endpoint/model fails the existing job rather than silently changing the provider. The provider secret is never stored in the row or returned to the client.

The coaching completion budget is bounded at 2,048 tokens. Groq requests use its documented `max_completion_tokens`. For Groq's exact `openai/gpt-oss-120b` and `openai/gpt-oss-20b` models the request sets `reasoning_effort:low` and `include_reasoning:false`; GPT-OSS does not support `reasoning_format`. The exact Groq `qwen/qwen3.8-27b` request sets `reasoning_effort:none` and `reasoning_format:hidden`. Unknown Groq models receive no guessed reasoning controls, and other compatible providers retain `max_tokens` with no Groq-specific parameters. This leaves room beyond the selected-ID JSON for internal reasoning while keeping the existing deadline and response ceiling. It does not establish real latency, a guaranteed successful completion or a free provider account. These controls were checked against the [Groq API reference](https://console.groq.com/docs/api-reference) and [model-specific reasoning documentation](https://console.groq.com/docs/reasoning) on 9 October 2026.

The only transition that can expose a reply is a successful database save guarded by owner, request, context, processing status and lease token. A failed save leaves no reply visible; a cancelled or replaced lease makes a late save a no-op. Complete responses read and validate the persisted row. Generated content is never returned directly by the provider-processing path.

Cancellation is a separate POST `{action:'cancel',requestId,contextDigest}`. Only pending/processing jobs change to cancelled. The server clears their retained context and lease; complete/failed receipts are preserved. GET leaves a cancelled receipt terminal. An explicitly consented start POST may resume the same cancelled receipt only within its original 24-hour age, with fewer than three prior attempts, unchanged provider binding and available combined outstanding capacity. Resumption preserves creation time, receipt identity and attempt counter. It is an existing job and does not mint another daily-quota receipt. Exhausted, expired or changed-provider receipts cannot be resumed. Cancellation does not delete completed feedback or revoke data already sent to the provider; an in-flight provider call may finish, but its cancelled lease cannot save a result.

Both AI endpoints share at most twelve new jobs per owner in a rolling 24 hours and four unfinished jobs. The predicates are part of the write itself, so concurrent v1/v2 requests cannot bypass limits. A new accepted request or explicit resumption fails unfinished jobs older than 24 hours once their leases expire and clears their retained input. This is lazy reclamation, not a scheduled deletion promise.

The high-level browser client API is `requestWorkoutCoaching(context,digest,{signal?}) -> Promise<{reply,accountId,requestId,model}>`. It discovers backend capability, sends explicit consent, follows the server retry interval, checks the current signed-in owner before polling and verifies saved reply identity and selected IDs. It has a 120-second total deadline in addition to each transport's 15-second deadline. Abort after an attempted start uses `cancelWorkoutCoaching(requestId,digest,{accountId,signal})` with a fresh three-second best-effort controller. The caller aborts for a closed view, changed local context or account; local encrypted persistence and rendering belong to the UI integration. Importing the client does not initiate a request.

## Privacy and retention

Remote coaching is a separate explicit request from encrypted account sync and local inference. Its minimized context is readable by the backend and configured provider. The server clears `context_json` after success, terminal failure or cancellation. Transient retryable failures retain context only while the job is unfinished; abandoned-job input is cleared lazily on the next eligible request. Saved selection JSON, provider/model identity, workout/context identifiers, status and receipt metadata remain on the server. This prototype has no automatic deletion of all completed receipts or account-deletion UI. The configured provider's own retention policy still applies, and cancellation cannot retract a request already received by that provider. No remote-model key belongs in a browser/native bundle or local coaching result.

The v1 metric-array and retrospective privacy description remains separate. V1 and coaching share quotas, but coaching includes explicit minimized profile, comparison and attendance context; it must not inherit a v1 claim that all AI requests send metrics only. An encrypted local coaching result contains the validated reply and binding metadata, not a duplicate readable remote context; the owning local-store/UI milestone controls its deletion and current-context checks.
