## Browser demo

Coaching has a collapsed optional Qwen sample, with three questions that retrieve reviewed sources. It uses a fictional completed adult workout, the exact existing default system prompt, and the publisher's pinned Qwen3 0.6B q4f16_1 model. The model selects at most two note IDs; visible prose is resolved from the reviewed original corpus. Model advice, loads, schedules, made-up URLs, extra fields, stale context and unknown sources are rejected. No saved workout/profile enters this demo and no automatic inference or device qualification is enabled.

Explicit download confirmation remains separate from Run. The worker reads only the existing app-verified cache, checks full file size/hash before use under the model lock, refuses WebLLM cache writes and network fallbacks, counts with the real tokenizer, and reserves 256 output tokens inside a 2,048-token context. Off, close, cancel, failure and stage-specific timeouts terminate the worker. Delete from the demo unloads it first. The main page retains its nonce policy without WASM/JavaScript eval; only same-origin runtime scripts permit WASM, with `connect-src 'none'` and no child workers.

Pinned packages: WebLLM 0.2.85 and web-tokenizers 0.1.6. The latter declares ESM but ships UMD; the adapter handles both its unbundled browser global and the actual bundler's CommonJS default export. Worker storage uses dedicated-worker APIs explicitly, avoiding the download view's `window` discovery. These defects were caught before publication. A separate reproducible Vite worker build runs before dev/build and keeps the multi-megabyte libraries out of the initial workout graph. Visited runtime files have a scoped offline-cache policy; real offline/browser acceptance remains pending.

## Real training, separate from the demo model

`training/qwen-evidence-v1` contains 132 original synthetic training cases and 34 separate validation cases. Examples use reviewed original notes, not archive records/abstracts, paper full text, forum posts, user histories or held-out answers. The default prompt and input files have exact fingerprints. Topic-template families, IDs and questions are disjoint between splits; repeated topics limit generalization.

An isolated official PyTorch CPU stack ran 16 real LoRA updates on 16 distinct examples, targeting query/value projections (1,146,880 trainable parameters). Base safetensors bytes and SHA-256 were checked at immutable HF revision `c1899de289a04d12100db370d81485cdf75e47ca`. The 4,602,248-byte adapter has SHA-256 `eac8cfe3ec8b994293ad9b2d19f5361c9a9a3ae49f8196b7e0cad6fdf390b437`; before/after parameter fingerprints differ. Runtime was 188.06 seconds with measured peak CPU-process RSS 5,036,859,392 bytes. These are float32 CPU measurements, not browser/phone memory requirements.

Four pilot validation cases had loss 0.087794 before and 0.001514 after. Loss is not accuracy. The unchanged 22-case held-out suite then ran independently in three fresh generation sessions: 39 actual model generations and 27 workflow/source-gated non-invocations. The automated rubric passed all 66 runs (accuracy and critical rates 1.0), with raw replies, real token/timing data and exact fingerprints preserved in `docs/evals/qwen-cpu-pilot-2026-10-09-*.json`. The evaluator receives no expected selections. CPU evaluation took 466.2 seconds at greedy sampling, distinct from the demo's temperature 0.7/top-p 0.8. This small synthetic result does not establish clinical validity, human relevance approval, browser/native accuracy or hardware qualification.

The trained checkpoint is exported separately with its tokenizer, actual training/evaluation report, default prompt and base Apache license. It contains no upstream model weights. The demo continues using the publisher model: a PEFT adapter must be merged/converted for MLC, receive a new immutable hash/byte manifest, then undergo final-artifact and real-device tests. No qualification record was invented and no model was published to a hosting service. Reproducible commands and limits are in `training/README.md`.
