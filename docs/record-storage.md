# Transactional local records

Private workout history now uses IndexedDB on web and SQLite through Expo SQLite on native. An encrypted root contains profile, plans, active workout, timer and an ordered history index. Each saved workout has its own AES-256-GCM envelope. Record type and ID are authenticated inside the ciphertext; the authenticated root binds each exact ciphertext digest. Keys remain bound to the existing vault ID, salt, purpose, schema and key version. This uses the existing crypto implementations, not a new cipher.

Crypto and validation finish before database transactions. A compare-and-swap transaction commits changed rows and the root together. The legacy localStorage/AsyncStorage index cache is written afterward; a projection failure restores the previous complete database root before returning an error. Cleanup runs after acknowledgement, checks the root again and never removes rows for a newer writer. Unchanged history is compared in memory after schema cloning; plaintext fingerprints are never stored.

A crash between database commit and cache projection may leave different originals. Web fails closed on a conflicting nonempty cache and database root and offers an original bundle containing both. It never guesses which profile to overwrite. A missing cache can be reconstructed after unlocking. Native treats its transactional database as authoritative. Complete original export takes one database snapshot so another writer cannot prune records halfway through export. A partial index alone cannot restore a nonempty archive.

Normal encrypted backups remain portable whole-state version-1 vault envelopes. Original-record recovery additionally supports version-1 `movefield-record-bundle` files, up to 32 MiB including cipher/JSON overhead. The state itself remains bounded to 5 MB UTF-8 and 5,000 history records. Original bundles can retain a differing legacy cache, which may be plaintext; the web download label/file name identifies that case. Schema/format failures preserve the originals. A lost native key requires the separate owner-held recovery key; a key is never silently minted over existing encrypted records.

Confirmed local erasure removes cache/draft/outbox before clearing the transactional database, and drops keys only after those deletions succeed. An interrupted database clear retains its root/records and recovery key. Native synthetic fault tests cover this path. Physical keychain behavior and filesystem remanence are unqualified; database deletion is not a secure-wipe guarantee. Android automatic OS backup is disabled for the prototype; explicit owner backups remain available.

Tests: `check-record-state.cjs` uses real SQLite files and fresh connections; `check-browser-records.mjs` uses real Chromium IndexedDB/WebCrypto. Both cover 100/1,000/5,000 synthetic archives. Browser checks also exercise storage failure, stale CAS, missing/substituted records, size limits and erasure. The native adapter runs the shared SQL adapter against real Node SQLite with a WebCrypto driver and mocked SecureStore/AsyncStorage boundaries. React Native Web checks exercise actual native components; neither these nor Hermes exports establish installed-device behavior.

This changes local persistence. Cloud backup remains an explicitly requested encrypted snapshot with conflict review; automatic background merge, setup-draft sync and cloud-key rotation remain unimplemented and require their own qualified protocol.
