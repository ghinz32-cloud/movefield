# Saved schema compatibility and new record identity

This source milestone addresses Claude C2 and the non-destructive portion of C14. It is based on recovered source `8abfca45f1f910155011516eabffbebdf070821b`, repository `ghinz32-cloud/movefield`, isolated branch `audit/2026-10-09-schema`. The parent engineering task owns integration, publication and exact-source web/native builds.

Every fixed-shape saved object now rejects unknown fields, including profiles, plan/session targets, proposal patches, set metrics, workout details, calendar events, custom exercises, audit rows, equipment limits and unfinished setup. The reader does not silently strip fields and does not trust arbitrary passthrough values. Unsupported saved versions ask the user to update while retaining the original records. A future timer field is also rejected rather than swallowed by the existing malformed-timer recovery fallback. Known invalid timer values retain their previous recovery behavior.

New records use secure UUID v4 identities. Existing IDs and references are untouched. The shared helper uses an injected secure byte generator or the runtime's Web Crypto API; it imports no Node/native dependency and does not access `window` or `document`. The native entry point installs Expo Crypto before rendering the application. Rest timer identities use the same helper. No time-based or Math.random ID fallback remains in these record creation paths.

Workout `timeZone`, `startedAtUtc` and `finishedAtUtc` fields are additive and optional. UTC strings must be canonical ISO UTC timestamps and exactly match the corresponding existing epoch-millisecond timestamp. The helper captures the runtime zone when a new workout starts and uses UTC only if zone support is unavailable. Legacy workouts keep their original IDs, calendar dates and timestamps; their original time zone is not guessed. Web/native start/finish capture is integrated by the parent task through `workoutTimeMetadata(now)` and `workoutFinishedAtUtc(now)`.

The schema stays at version 2. A complete version-3 migration has not been performed: local state, encrypted history heads, transfer files and runtime writers currently share the version-2 contract. Changing that literal independently would break existing records. The additive change plus explicit incompatible-data refusal removes silent loss while retaining established readers. A future bidirectional migration must version those boundaries together. Older installed builds still have their older parsers and cannot be retroactively repaired by this source change.

The obsolete `simulatedOffline` flag is accepted solely for compatibility and normalized to false when records open. A legacy fake-queued proposal becomes stale and requires another review. Other records and targets are preserved. This flag does not represent real network state or a synchronization acknowledgement. The real offline mutation queue is owned by the separate synchronization milestone.

`readSavedState(raw, {maxChars})` accepts an explicit integer character bound up to 24,000,000 for the parent's trusted stored-record reader. Its default remains 5,000,000. This change does not remove nested record bounds or provide unbounded parsing. UTF-8 capacity enforcement belongs to the separate capacity adapter.

Validation includes 1,087 focused compatibility, unknown-key, unchanged-input, stored-limit, UUID and UTC/zone assertions; 29 security checks; and native storage fixtures that try both reading and overwriting encrypted unknown-field/version-3 records and verify every ciphertext and secure key remains byte-for-byte unchanged. Web/native types, changed-source lint with zero warnings and 40 canonical shared hashes are checked. The final suite result is recorded beside this report. Initial broad failures were test harnesses with fixed transpilation file lists and earlier tests intentionally expecting unknown-key stripping; those tests were updated for explicit rejection and their targeted reruns passed.

This is source/harness validation. It does not establish physical-device execution, native signing, synchronization service provisioning, a live deployment or application-store acceptance.
